# Scratch launch candidate — local only

## Architecture and activation
This candidate is based on security-patched commit 307d649; it does not publish the old mixed prototype checkout. Gameplay art/CSS and canvas behavior are copied selectively. No prototype localStorage identity, prize controls, deterministic boards, or hidden unchosen symbols are accepted in production. Only cosmetic coating coverage remains client-side.

A dedicated PostgreSQL database is required. Apply `migrations/001_scratch.sql` once as migration owner; never auto-migrate at web startup. Give the web/worker role SELECT/INSERT/UPDATE on player/session/verification/card/request/outbox/rate, SELECT plus column-level UPDATE(free_remaining) on campaign, and SELECT/INSERT only on event. No table ownership/superuser, schema creation, or event deletion. A separate report role can have SELECT only. Restrict database networking, use transport encryption/private connectivity, and verify backup/restore before activation.

No default campaign or real weights exist in migrations. Explicitly insert approved campaign ID, enabled=false initially, UTC start/end, integer weights for all four keys `25`, `40`, `50`, `free`, approved rules, free inventory and fulfillment. At least one discount must have positive weight; capped free depletion then falls back proportionally to discount weights. This does not alter fair 1/6 card win odds. Never copy synthetic test settings into a live campaign. Configure business-approved eligibility, claim deadlines, and truthful free-ticket fulfillment before enabling free prizes.

Protected runtime settings (no values in source):
- SCRATCH_DATABASE_URL; SCRATCH_CAMPAIGN_ID; SCRATCH_ORIGIN (canonical HTTPS origin, no path).
- SCRATCH_ENABLED=1 enables the invitation, /scratch and API; absent means unavailable. The layout is deliberately dynamic so the runtime kill switch removes the invitation without rebuilding.
- SCRATCH_CRM_URL: exact HTTPS scratch-intake endpoint; SCRATCH_INTAKE_TOKEN: dedicated server credential. CRM must separately allowlist promotion ID and have reviewed schema/grants/consent intake deployed.
- Concrete AWS SES transport: SCRATCH_MAIL_PROVIDER=ses, SCRATCH_SEND_ENABLED=1, SCRATCH_FROM_EMAIL (verified sender), AWS_SES_REGION, optional AWS_SES_CONFIGURATION_SET, protected AWS SDK credential chain. Default restricted test-recipient mode requires exact SCRATCH_TEST_RECIPIENTS. Public rollout must explicitly set SCRATCH_MAIL_MODE=live after approval; this is not configured here.
- Optional existing idempotent broker alternative: SCRATCH_MAIL_PROVIDER=broker, SCRATCH_MAIL_URL and SCRATCH_MAIL_TOKEN. HTTPS broker must accept `{to,subject,text,html?,idempotencyKey}`, honor `Idempotency-Key` across ambiguous retries, and return `{id}` only after provider acceptance. No new broker is required for SES.

Verification emails use a short-lived random code entered into the originating browser tab. No token in URLs, referrers, analytics, or HTML. Eight attempts per code, fifteen-minute expiry; 30-day HttpOnly SameSite=Strict revocable session. Code payloads are scrubbed after provider acceptance or when expired/used. A lost verification response requires a new request; no silent success is claimed. Signup consent/profile are bound to each verified challenge: an earlier unverified signup cannot inject marketing consent into a later verified signup.

## Worker and operator reporting
Run `npm run build` during image/build preparation; it compiles the TypeScript worker/operator to scratch-runtime with no runtime TypeScript dependency. Package that directory alongside package.json/package-lock.json and production dependencies (`npm ci --omit=dev`) for a separate worker/operator process; Next standalone output alone does not automatically package this worker. Run commands inside the protected deployment/operator environment with credential injection; do not paste connection strings or tokens into chat/CLI.

- `node scratch-runtime/operator.cjs report`: private JSON aggregate. For sharing, use aggregate output, never database dumps or raw contacts.
- `node scratch-runtime/operator.cjs work`: up to 100 pending jobs. **This performs sends when configured; not run against real providers during this task.** Schedule only after protected provider binding and send approval. Leasing, retries/backoff, six-attempt terminal failures, idempotent keys and stale-worker fencing included. SES has no idempotency key: its jobs are durably marked UNKNOWN before network dispatch, SDK retries are disabled, and only explicit acceptance clears UNKNOWN. Definite provider rejection may retry; connection timeouts/process crashes remain UNKNOWN and are never automatically resent. Reconcile using SES configuration-set events and opaque scratch_job tags before any manual requeue. This avoids duplicate emails but can require operator recovery after a pre-send crash.
- `node scratch-runtime/operator.cjs retry JOB_UUID`: requeue a terminal failed job for another attempt (no immediate send). Expired verification jobs remain unusable; request a fresh code.

CRM consent is optional, captures version/timestamp, and preserves CRM suppression semantics. A CRM failure does not erase a player's game or award. Prize mail requests dedupe per award. Requested/pending/provider-accepted/failed/acceptance-unknown are separate; provider acceptance is **not delivery**. Verified SES/SNS delivery/bounce/complaint/reject ingestion is implemented at /api/scratch/ses-events. Bind SCRATCH_SES_TOPIC_ARN to the exact approved topic and configure the SES configuration set/SNS HTTPS subscription through approved operator setup. This endpoint verifies the AWS certificate host, exact topic, timestamp and cryptographic signature before accepting an event; it never follows subscription confirmation URLs. Confirm the subscription separately via AWS controls. Duplicate events dedupe; adverse outcomes cannot be overwritten by delayed delivery events; signed receipts resolve uncertain sends. Real topic configuration and controlled inbox acceptance remain unverified. No opens/read claims are made.

## Analytics
`report` includes client observations vs authoritative server outcomes, observed tab-session counts (30-minute window, not unique people), registered/verified-player counts, card starts/completions, daily three-card use, win/loss, square/choice/method, completion timing, award tiers, prize reveal/claim, mail state, failures, and source/device/placement cohorts. Client event intake uses strict name/property/category allowlists and ID dedupe. Attribution is observational/user-supplied, not authenticated acquisition truth. Unfinished cards idle thirty minutes are inferred inactivity, not confirmed abandonment.

Only coarse category metadata and opaque temporary observation IDs reach analytics. No email/name/token/IP/full user agent/raw URL query or arbitrary error string. Internal player links never reach Google Analytics. Scratch-page GA context strips all query parameters including UTM; existing ordinary homepage ticket tracking remains. Scratch events use first-party aggregate storage, not an unconfigured GA-only stream. Mirvish exact links are measured explicitly without decorating their redemption query. Outbound intent is **not purchases or revenue**; Mirvish conversion integration is absent.

## Required launch gates and rollback
1. Owner-approved prize distribution, free stock/dates/fulfillment, campaign window/eligibility/consent contact details.
2. Bind the implemented SES adapter to protected credentials/verified sender (or an existing idempotent broker); verify account sandbox/recipient authority and provider responses. Controlled inbox test requires send approval. Bind/test real CRM intake without changing suppression flags.
3. Provision isolated production DB/runtime/report roles, backups and restore proof; migration approval. Test grants as restricted runtime (synthetic role already tested).
4. Bind per-IP/network ingress rate limiting at trusted reverse proxy; code has global + session/email durable limits but does not trust arbitrary forwarded IP headers. Confirm mail abuse safeguards at realistic load.
5. Choose/implement retention and purge schedule for PII, expired sessions/challenges, cosmetic browser state, raw events and request keys; backup retention must agree. No new schedules installed here.
6. Physical iPhone/Safari touch, live Mirvish discounted checkout all three tiers (without purchase), full parent acceptance. Shared Mirvish codes are not one-use entitlements.
7. Commit/review/push and separately approved deploy; preserve existing website security baseline. No production activity was authorized/performed by this implementation.

Stop new play via campaign.enabled=false while allowing verified users to retrieve existing awards; complete kill switch SCRATCH_ENABLED unset removes all public access. Stop worker separately to stop sends. Code rollback to patched pre-feature image leaves additive DB data intact; do not drop campaign records/outbox or replay sends. Backup state before schema/grant changes. Public signup should remain disabled until above gates pass.

## Approved policy and private fulfillment
Initial free inventory: SIX PAIRS total. Discount-only mix: 70% at25, 20% at40, 10% at50. Free frequency is NOT approved: `scratch-campaign-policy.json` leaves it null and campaign disabled. `approvedWeights(percent)` rejects null and converts an explicitly approved whole percentage into weighted winning awards while preserving conditional discount mix. Never activate with a guessed value. Once free stock is exhausted, discounts use their approved conditional mix.
Free awards enter `scratch_fulfillment` in the same transaction as inventory consumption. No external staff email is sent. Staff follow up by email and book tickets manually. Protected operator `fulfillment` displays name/email and award/status; handle as private personal data, never publish as analytics. `fulfill CARD_UUID contacted|booked` changes monotonic status only; use a dedicated operator role with SELECT on relevant player/card/fulfillment and UPDATE(status,updated_at) on fulfillment. Public runtime needs SELECT/INSERT on fulfillment only. `cap TOTAL_PAIRS` needs campaign column UPDATE(free_remaining), locks campaign and computes remaining from existing awards. Initial setup uses6; later increases do not replenish previously consumed awards.
